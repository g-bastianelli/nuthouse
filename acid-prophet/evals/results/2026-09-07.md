# Acid Prophet behavioral refactor observations

Date: 2026-09-07. Baseline source: `703024dbc23e93defca2514c1692c282edb23fa2`.
Candidate: the Acid Prophet 1.1.0 working-tree revision accompanying this record.

These were actual task executions in disposable repositories created by `prepare.mjs`,
using fresh Codex collaboration agents with the inherited model and no model override.
The exact served model identifier was not exposed by the dispatch result. Auditing inside
generation runs used the snapshot's instructions. Evaluators received no scoring rubric
or expected answer. No production repository or external service was changed by a run.

The contradiction case was identical on both sides: Solution/Error handling forbid
viewers with 403, while AC-002 requires a viewer success with 201. The candidate cited
those sections and the existing authorization guard, and failed `behavior-consistent`,
`acceptance-defined`, and `clarifications-resolved` without choosing a new policy.

The boundary case describes one adapter isolating exceptions from an injected audit
sink, with one explicitly named consumer. The baseline blocked solely because a second
consumer was absent and warned that a file explicitly labeled new did not exist. The
candidate accepted the justified boundary. An initial trial's fixture used the inaccurate
word "existing" for the sink; it was corrected and the baseline was rerun against the
same corrected fixture used by the candidate. The table records that controlled pair.

Both generated specs were read after execution, along with their actual audit artifacts.
They reused `validateNote`, preserved role/email validation precedence, made missing
versus null notes explicit, documented the code's UTF-16 length convention, and covered
invalid/forbidden outcomes. Both remained `status: draft` with `verified-by: _none_`.
The candidate's parsed audit contained seven complete gates and zero findings.

## Planning forward run

`plan-existing` was run against the candidate only; it is not a before/after comparison.
The agent produced one coherent deliverable covering AC-001 through AC-005, with files,
symbols, dependencies, expected outcomes, and five concrete quickstart scenarios. The
empty contracts directory had an explicit rationale: no new interface shape was needed.
The complete six-field handoff included `_none_` for the absent constitution.

A fresh reviewer reported zero blockers and warnings. On the unchanged fixture,
scenarios 1, 2, 4, and 5 passed, while scenario 3 failed as documented and reproduced
the invalid-note defect. Future implementation tests remained explicitly unverified.
The final files were read after the run: the plan was `status: validated`, carried a
real validation timestamp and exact source version 1, and preserved all five source
ids. All named artifact paths and the review artifact existed. Production source in
both generation runs was byte-for-byte unchanged.

## Deterministic regressions

Three tests were run against the original parser and failed before it was replaced:

- A claimed yes overrode a failing gate and blocker.
- An incomplete gate list authorized handoff.
- A zero-blocker count concealed a blocker in the report body.

The replacement derives eligibility from complete gates and actual findings, rejects
inconsistent counts/duplicate entries, and preserves an explicit no. During the planning
forward run, the auditor rendered an empty auto-fix marker as a bullet. A separate test
reproduced its accidental interpretation as a proposed mutation, then verified the fix.

## Interpretation

The audit comparisons demonstrate two corrected behaviors in the observed runs. They
do not establish a success rate, performance improvement, or superiority to another
skill collection. Broader claims require repeated runs on more tasks and models. The
generation comparison retained an already working behavior rather than inventing a gain.

The generic `skill-creator` metadata validator rejects this repository's existing shared
runtime keys (`model`, `effort`, `argument-hint`). The repository's own metadata and Codex
agent parity tests validate those supported conventions; the generic rejection was not
treated as evidence that the behavioral evaluations passed.
