## Predicted cost and observations to capture

For N selected issues that reach reservation, the reservation phase drops from 4 reader
dispatches per issue (selected + members, twice) to 2. It also removes duplicate direct
issue reads for team/status and exact readback. A valid same-team status resolution can
serve later issues in that invocation. Initial selected detail reads are per issue to keep
each preparation independent, so they grow from one batch reader to N bounded readers;
overall initial + detail + reservation reader requests become `1 + 3N`, versus `2 + 4N`
before, excluding event/control entry, recovery, and the optional fresh refill. These are
contract-derived request counts, not measured tool latency or token usage.

For project reads, relation hydration is proportional to candidate members rather than
all members. Complete membership/status pagination and direct external-blocker evidence
remain mandatory. Ready B no longer inherits slow A's setup delay; only the short serial
reservation/verification/launch of another ready issue can precede it. A first-host probe
can still deliberately delay every issue on that host until actual reception is known.

Execute the same cases with mocked responses in each runtime before claiming measured
latency improvement. Capture reader/service calls, time to first verified launch, each
workspace's setup-ready and launch times, loaded characters/tokens when exposed, exact
status write fields, number of launches, and refill count. Separate fixture time from
live-service time. Do not substitute source review or unit-test success for runtime
reception, race safety, or a delivered PR.
