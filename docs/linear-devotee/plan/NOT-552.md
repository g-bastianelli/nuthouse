# Plan — Integrate adaptive project creation (NOT-552)

## Context

NOT-552 makes `linear-devotee:create-project` consume the install-local adaptive workflow decision and coordinate one profile-appropriate artifact/cascade run. The ratified project-creation child spec is authoritative for AC-019–AC-023, while the parent kernel owns decision-manifest validation, profile resolution, immutable gates, and cross-plugin handoff identity.

## Risks

- The shared kernel currently resolves generic immutable gates; project-specific artifact requirements belong in Linear Devotee's domain mapping, keyed by the effective profile/capabilities, rather than by changing kernel policy in this issue.
- Prompt/runbook integration can describe a loop unless ownership and return contracts are exact. Require a single `run_id`, validated manifest handoff, stable artifact ids/content hashes, completed-capability ledger, and explicit return target on both sides.
- The existing cascade already has strong graph and payload-hash semantics. Adaptive state must be additive and must not create a second preview hash, second approval, alternate mutation projection, or retry path.
- Strict artifacts can be conditionally applicable. Constitution gates are required when the workflow decision enables them; absent non-applicable constitution content must be represented explicitly instead of fabricated or silently treated as complete.
- NOT-551 owns generated install-local workflow bundles. This issue consumes those bundles and must keep `check:workflow` green without hand-editing generated files or introducing repository `_shared` runtime imports.

## Out of scope

- Changes to the canonical workflow kernel, generated bundles, classification/profile precedence, risk floors, manifest storage implementation, or runtime adapter parity owned by NOT-547–NOT-551.
- Creating a real Linear project, milestone, issue, dependency, or graph receipt; implementing any generated project issue; starting Maestro; or marking unrelated Linear work complete.
- Replacing the project graph/envelope implementation, changing stable Acceptance ids, adding a second orchestrator/approval gate, requiring Warden, adding dependencies, committing, pushing, opening/merging a PR, or mutating the ratified specs.
